# 公司管理与钉钉通讯录

## 公司维护

管理员登录后，左侧进入“公司管理”，可新增和修改公司编码、名称、上级公司和备注。按左侧公司层级筛选包含其下级的公司，按编码、名称或备注搜索。

公司由系统内手工维护。钉钉仅提供部门、人员及其隶属关系，同步不会新增、改名或覆盖公司。公司编码支持字母、数字、点、横线、下划线；公司编码和名称不重复。上级不能选择自己或自己的下级，同时编辑同一公司时会提示刷新后重试。所有保存均有管理员审计记录。

升级时从现有资产、员工资料的公司名称初始化公司，不修改原资产。自动生成的 C0001 等编码可在页面改为实际公司编码；不从公司名称猜测上下级关系。后续仅手工维护公司。公司改名后，旧台账及审批快照保留原名，旧名称仍关联同一个公司用于统计，不允许将另一家公司命名为该公司的历史名称。

## 钉钉配置

服务端部署环境配置以下三项，重启服务后生效。AppSecret 仅存服务端，不进入前端构建、浏览器存储或接口返回。

```ini
DINGTALK_CORP_ID=企业CorpId
DINGTALK_CLIENT_ID=企业内部应用AppKey
DINGTALK_CLIENT_SECRET=企业内部应用AppSecret
```

在钉钉开放平台为同一企业内部应用授予部门信息、部门用户详情的读取权限，以及所需通讯录授权范围。权限名称和可选范围以企业当前后台及官方文档为准。仅配置应用使用范围不等于授予通讯录接口权限。

相关接口：

| 用途 | 服务端接口 |
| --- | --- |
| 应用令牌 | `POST https://api.dingtalk.com/v1.0/oauth2/accessToken` |
| 部门详情 | `POST https://oapi.dingtalk.com/topapi/v2/department/get` |
| 直接子部门 | `POST https://oapi.dingtalk.com/topapi/v2/department/listsub` |
| 部门用户详情及分页 | `POST https://oapi.dingtalk.com/topapi/v2/user/list` |

参考：[获取企业内部应用 access_token](https://open.dingtalk.com/document/development/obtain-orgapp-token)、[获取部门列表](https://open.dingtalk.com/document/orgapp/obtain-the-department-list-v2)、[获取部门用户详情](https://open.dingtalk.com/document/orgapp/queries-the-complete-information-of-a-department-user)。公开文档页面可访问，但接口正文使用动态加载。本次按现有接口契约及模拟响应完成自动化验证，真实企业的权限、限流和字段可见性仍须使用实际应用联调。

## 同步与归属

1. 进入“组织与人员 → 同步设置与记录”，填写授权起始部门编号。完整组织通常从 `1` 开始；部分授权时填写可访问的起始部门，多个用逗号分隔。
2. 点击“立即同步”。后台递归获取部门、分页获取人员，以企业及钉钉 userid 保持稳定身份，重名人员不合并。获取姓名、工号、职务、部门及可见的稳定身份字段，不额外保存手机号等字段。
3. “组织架构”中展示部门层级，点击部门查看其下人员。“员工列表”支持按公司、部门及关键词筛选，展开查看每个部门及对应公司的关系。员工兼职多个部门时不丢失关系，汇总展示字段过长时截短，完整关系单独保留。
4. 可在“公司管理 → 修改”选择公司对应的钉钉部门。此设置可选，未绑定不会影响手工公司维护。部门向上寻找最近的公司绑定；未命中时使用“未绑定部门的默认公司”，或保持未分配。
5. 可设每 30 分钟、每小时、每 6 小时或每天同步。后台任务最长 15 分钟，同一服务只执行一项通讯录同步；同步期间不能修改公司和同步设置。退出当前页面不取消同步，重启中断会在再次启动时记录失败，可重新发起。

同步全部读取成功后才在事务中保存。接口失败、分页异常、字段超长、部门循环或数据库保存失败会回滚，保留原通讯录。令牌失效会刷新并重试一次。授权范围不再读到的员工标为待核对、撤销关联登录会话；不直接删除员工、资产或审批历史，也不自动恢复手工停用的账号、变更既有角色。

旧台账只有姓名时，管理员在“旧台账关联”结合部门和工号逐项确认。同步不会按姓名自动绑定资产，也不会因人员调岗而自动改写资产使用部门或历史审批单据。

## 升级与本地验收

停止旧 Go 服务，使用升级账号执行新版本 `asset-migrate` 创建 `companies`、`company_names`、`employee_departments` 三张新表，保留已有数据，再启动新服务并更新前端静态文件。运行时 MySQL 业务账号需要访问新表；部署脚本仍适用。SQLite 只读迁移兼容不包含这些表的旧库，已另外用旧 SQLite 向独立空库验证 1,762 条资产复制及 17 家公司初始化。

本次在独立 MySQL 测试库通过：公司新增/编辑、循环与重复校验、版本冲突、旧名关联统计、管理员权限；嵌套部门与分页、跨部门人员去重与归属、令牌刷新、接口失败及错误记录、异常分页保护、人员缺失标记、后台任务与配置互斥；原有审批、资产、导入导出及权限回归。前端 18 项测试、类型检查及构建通过，浏览器完成新增/编辑/搜索、组织树筛选、默认公司设置和 390px 手机视口检查。

本地预览 `http://127.0.0.1:33000/` 保留 1,762 条资产，公司名来自现有台账。真实钉钉应用凭证尚未配置；模拟验证通过不代表已连接企业通讯录。企业配置完成后需核对部门总量、人员数量、兼职部门、授权范围变动，以及管理员/普通员工的实际访问结果。
